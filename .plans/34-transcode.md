# #34 Live transcode: fast profile, audio paths, subtitles, admission cap, startup trial

## Summary

Live transcoding on top of the #33 remux sessions. A transcode plan opens a session and returns a master playlist URL, like remux. The transcoder runs one ffmpeg per session with the fast live profile: video re-encoded on the CPU to the ladder rung the engine chose, tone mapped to SDR when the decision says so, keyframes forced on the Item's segment timeline; audio copied, re-encoded to EAC3 5.1 or downmixed to AAC stereo. Text subtitles become WebVTT renditions in the master playlist, converted on demand. A bitmap subtitle the client cannot render is burned in. Transcode sessions pass a per-transcoder admission cap, default 2; a session beyond it is queued, its registry state says `queued` with a `session.state` event, and it starts when a slot frees. At startup each transcoder runs a 2 s trial encode per backend and writes the capability table on its node row; readiness waits for it, the CPU backend must pass, and hardware backends are recorded when their trial passes.

Read: CONTEXT.md, docs/spec/transcoding.md, playback.md, topology.md, ADR 0003 and 0009, docs/research/ffmpeg-hls-pipeline.md, `.plans/33-hls-sessions.md`, apps/server/src playback and transcoder, and the #39 player on `stack/39-player` for the client contract.

- No B-frames on the live profile. Measured with ffmpeg 7.1.5: libx264 with B-frames under `-copyts` writes fMP4 fragments whose video starts two frames (80 ms at 25 fps) after the boundary, because movenc sets the fragment start from the first pts. `use_editlist=0` fixes a restart but writes a negative `tfdt` for the run from zero; `negative_cts_offsets` still shifts by one frame. With `-bf 0` the first frame of a run at 6 s has pts and dts 6.000. AV1 has no reorder at the container level.
- Every segment file now carries its own header. The mp4 muxer writes an AC-3 or E-AC-3 sample entry only after the first packet (`delay_moov`), and the segment muxer's shared header file cannot wait for it: with `empty_moov` alone ffmpeg refuses ("Cannot write moov atom before AC3 packets"), with `delay_moov` and a shared header the first segment's media lands in the second file. So #33's remux copy of an AC-3 source failed too. Runs now use `-individual_header_trailer 1` with `delay_moov+skip_trailer`; each `N.m4s` is `ftyp moov moof mdat`. The run reports each segment with the offset of its first `moof`; the session serves the bytes from there and keeps the first segment's prefix as `init.mp4`. Measured: the prefix is byte-identical across segments and across a restart, for copy and for re-encode.
- The CPU tone map names every zscale input (`tin`, `pin`, `min`, `rin`). With only the first stage tagged, zscale fails with "no path between colorspaces" on frames whose tags it dropped. libx265 writes colour tags only from `-x265-params colorprim/transfer/colormatrix`, so the HDR fixtures set those.
- Forced keyframes list only the boundaries after the run's start. ffmpeg consumes one forced time per encoded frame, so a restart at segment 300 with the full list would make its first 300 frames keyframes.

- A WebVTT conversion reads the whole File, so on a large remux over NFS the first request for a track can take a while; a failed conversion is not cached. It runs per session and dies with it.
- The cap counts transcode sessions, not remux runs. The spec says "concurrent ffmpeg processes"; a remux copies at about 1000x realtime and finishes in seconds, so counting it would let two remuxes block a transcode. A session holds its slot until it stops, so a paused viewer keeps their place until the 60 s idle stop.
- Only a `starting` session becomes `queued` in the registry. A session that was `playing`, idled out and revives behind a full cap waits the same way, but its registry state stays `playing` so the player's heartbeats still land.
- Hardware backends are trialled and recorded, never chosen: this slice builds CPU arguments only, so planning reads only the `cpu` entry. Choosing a hardware backend comes with its argument builder.
- Burn-in takes the first bitmap subtitle Stream whose decision is `burn`. The engine marks burn-in whenever the client cannot render a bitmap Stream, without a viewer's subtitle choice, so every Blu-ray remux with PGS transcodes for a browser today. That rule predates this slice (#24).
